# Review requirements

Apply the supplied shared product-quality skill before authoring or reviewing.

The lifecycle author exports the complete exact review context and requests a fresh independent reviewer through the root. The manager authenticates and registers the returned verdict using the direct review registration command supplied in the guidance. The author submits that exact unchanged verdict using the normal submit-proposal command. Do not author your own review or replace the registration with completionEvidence. The following content judgments belong to the independent reviewer.

Independently review the complete RQS and its contained requirement graph against the stakeholder request. Check that software descendants collectively fulfill their parents and that leaves give appropriate implementation and verification contracts. Apply every shared reviewer check, including one obligation, the architecture/depth decision and a requirements-only reader's ability to derive behavior. Bundling, unresolved required semantics, and unneeded or over-specified obligations are content defects, not optional editorial preferences. Judge clarity, scope, assumptions and relevant interactions. Apply typed-requirements' shared allocation/depth, supporting-note and complete-refinement checks. A system duty allocated to one element or jointly to several is valid; check that rationale names contributions and boundaries while every required behavior appears in normative content. When levels are used, mark needs-change missing or unsuitable software responsibility scopes, unjustified technology in a system/HLR, repeated obligations, reversed abstraction or unresolved scope relationships. Useful nested system/HLR/LLR refinement needs no fixed tiers. Review cross-scope contributions against the stated software-item boundary and exact ICDs, not labels-only equality. An allocated system leaf is valid only when its contract is fully settled; it cannot conceal missing meaningful refinements. Judge collective adequacy at every immediate group, including joint integration and progress when no external event arrives. The CLI owns structural and graph checks.

A staged set is reviewed one stage at a time. The first stage contains only stakeholder roots: judge each root against the stakeholder request and judge whether together they capture the agreed scope; no decomposition is expected yet. Each later stage adds one group to a set whose earlier stages already passed. Its assessment frontier lists only the new requirements and group. Judge those children under their parent and against their siblings already in the graph. A defect found in an earlier passed record belongs in `findings` with an explicit correction target, not in a re-assessment of passed rows.

In the exported `requirementGraphs`, use the entry whose `selection` equals the reviewed RQS revision. Populate `requirement_assessments` with exactly its `assessment.requirements` revisions, each once, and `decomposition_assessments` with exactly its `assessment.groups[].revision` values, each once. Each group's `children` rows must contain exactly its listed `assessment.groups[].children` revisions, each once. These arrays follow the exported assessment frontier while the complete graph remains review context. Record judgments of retained requirements and groups outside that frontier in `findings`, and include those judgments in the set-level outcome.

Each DCP assessment concerns its exact parent and immediate children. Apply typed-requirements' parent counterexample check to that selected group, including its timing and workload conditions when the parent promises a timed outcome. Judge the child's complete obligation for validity, then its contribution to this parent separately from collective adequacy. For example, a shared child that both invokes several operations and associates returned results with requests still contains those separate duties when reused under a parent for one operation. Discussing only that operation's fragment does not establish the child's validity. A coherent shared result-classification rule may still serve several parents. For a group marked `needs-change`, identify a parent requirement or immediate child assessment marked `needs-change`, or set `membership_action` to `revise-membership` when additions, removals or redistribution are needed, even if all existing children remain valid. Record deeper descendant defects in their owning assessments. Keep an ancestor group `adequate` when its immediate decomposition is sufficient; any defect in its own parent, children or membership still needs an explicit correction target. Return one set-level outcome consistent with all assessments: adequate ancestor groups can coexist with a failing outcome for descendant defects.

Use the supplied direct proposal guidance and payload schema. The CLI supplies identities, exact required links and publication markers. Submit the authored values with mdlm proposal submit. Keep the body empty when the structured payload contains the whole claim.

For each `informed-by` link in the requirement graph, read its exact EXP/OBS origin in the supplied review context's `records`, matching `revision_id` to the link target. Judge necessity against stakeholder intent and the stated formal scope. An origin link explains derivation; it does not prove correctness or establish stakeholder acceptance. Check that adjacent exploratory choices have not silently become obligations.

Read the exact ICD records supplied in interfaces. Apply typed-requirements' normative ownership rule: assess the applicable stable clauses named by each owning REQ, and report required behavior found only in rationale or without an explicit owner. Judge those obligations against both endpoint responsibilities, assumptions and integration evidence. Referenced descriptive or provisional design choices are not automatically requirements. Old interface evidence applies to its exact bindings; a revised contract needs an explicit applicability assessment. When the set retargets an agreement, the graph's `interfaceRetargets` lists each unchanged requirement whose binding moved from `bound` to `selected`, and those requirements are back in your assessment rows. Compare the clauses each one cites in both revisions. Mark it `valid` only if its unchanged wording still states the right obligation under the new clauses; otherwise mark it `needs-change`.

Apply the design-criteria skill: check each new requirement's normative content is an outcome with a requirement-tier source; mark a mechanism written as a requirement `needs-change` with rationale `reclassify` only when the first-match test places that mechanism in the design-criterion tier, and mark a design criterion that is really a stakeholder-owned, outside-contract or never-demote outcome `needs-change` with rationale `reclassify` (criterion → requirement). Review recorded design criteria once for coherence and feasibility. Findings about correctly classified choices are nonblocking unless they endanger a requirement or protected outcome; misclassification is blocking, including when the missing outcome has no normative owner yet. Check that open provisional requirements have a closing plan. For stakeholder roots, check that each traces to a stated intent sentence or stakeholder decision, uses the stakeholder's terms and carries no protocol detail, interface clause or unstated number; an obligation with no stakeholder source is `needs-change` unless it is a derived obligation the stakeholder approved. Roots stay at stakeholder granularity, one outcome the stakeholder would recognise; split a root that bundles independent stakeholder outcomes, but do not ask for one coherent outcome to be split into several roots for finer detail; that detail belongs in software children. Do not require durability above the operating profile's level, more than the protected outcomes for a race inside an already-warned window, or stakeholder questions for edge-case limits the author may state (design-criteria). For an interface, check that it names its trusted platform components and does not re-specify them, and that obligations for input no named caller sends are limited to the operating profile's protected outcomes. Check that every input dimension the product itself interprets is bounded or explicitly declared unbounded with a rationale: sizes, counts, lengths, rates, durations and optional parts such as a request body. A universal clause such as "refuse every request that is not X" is `needs-change` unless X is fully settled; otherwise each implementation review finds the next unstated input case. Check that the interface clauses and requirements a group relies on can all hold together for every input a named caller sends, including timing against validation: a deadline and a duty to refuse invalid input conflict when, under the stated bounds, the input needed for that decision can arrive too late to validate and refuse within the deadline. When they cannot, mark the owning requirement `needs-change` and give a concrete counterexample input.
