# Review product implementation and current evidence

A fresh reviewer inspects the exact product against reviewed requirements and public ICD obligations. Check production attribution and honest file roles using source-trace guidance. Review the selected independent activities, their adequacy judgments, current case results and actual captured evidence. Compare the union of obligations covered by all selected activities with every requirement as written, including parent-level integration claims. Return fail if any obligation is missing even when each individual activity has a passing adequacy review. A passing process exit alone does not establish complete coverage.

For each unchanged selected verification activity, authenticate the exact accepted passing independent adequacy REV and its scope. Where that activity permits reliance, its independently reviewed synthetic controls may establish the method's ability to accept permitted presentations and reject contradictions; implementation review need not repeat those same control judgments solely to establish independence. Preserve every explicit activity obligation. Reassess controls when the method, execution assumptions or relevant evidence differs, or a concrete adequacy concern remains. Independently assess every current product requirement, frozen semantic criterion and complete current observation and source scope. Method adequacy never substitutes for product conformance.

Implementation review has source access, unlike independent verification authoring and coverage review. Preserve that distinction. Judge whether the exercised product matches the recorded exact source and intended operational scope. Include coverage_assessments for every exact selected requirement, with disposition adequate or needs-change and rationale explaining how the selected activity cases collectively cover its obligations. Return concrete findings or pass. The manager registers the complete independent proposal and the author submits those exact bytes.

For an explicitly opted-in formal collection and independent postrun inspection method, use the full existing review context, including frozen VFY criteria, exact executed verifier source, receipt, report, streams and complete captured observations. Judge every frozen semantic criterion for each exact requirement and case, including associations, qualifications, negative behavior and integrated conditions. Record a supported PASS, FAIL or incomplete conclusion with precise source or captured-evidence references in findings and the relevant coverage_assessments rationale. A case-level conclusion covering several criteria passes only when all pass. A contradictory whole message fails even if it contains expected words.

Collection PASS establishes only the declared executable assertions. Return pass with adequate coverage only when the combined evidence establishes every selected requirement. Return fail and needs-change coverage for a semantic violation or an unresolved evidence gap, describing which it is. Preserve raw fail/error/skipped outcomes; judgment cannot promote them. Read missing already-retained metadata before registration, preserving intermediate assessments, and register only after reaching a supported conclusion or identifying a genuine evidence gap. This option uses the existing formal implementation REV; it supplies no pending semantic pass for prototypes.

When the implementation follows a requirement and a concrete counterexample shows that the rule itself fails the stakeholder outcome, include an explicit requirement_assessments needs-change row for that exact selected requirement. Name each assessed requirement once. Coverage needs-change alone identifies missing or inadequate evidence and does not authorize rewriting the requirement. A passing Review cannot carry a needs-change requirement claim. The failed Review preserves the counterexample for the existing requirement correction route; findings outside approved change scope require stakeholder scope amendment.

Name any incorporated exact ICD clauses that the counterexample depends on. A stronger README or external stakeholder ruling cannot substitute for a corrected lifecycle requirement. Record an authorized departure explicitly as a departure; do not describe it as satisfying the unchanged requirement.

When a result carries historical_observation, inspect its original RES and predecessor IMP, unchanged source and attribution, exact retained method, original receipt/report/streams/artifacts and execution times. Its successor links scope the current applicability claim and do not claim a new execution. The kernel authenticates recorded bindings and disqualifying attempts; you still judge every current obligation, shared assumptions, environmental relevance and freshness, including implications of changed siblings or unresolved relevant findings. Require a fresh run when the claim needs another sample or an unknown relevant runtime condition. Historical evidence transfers no earlier implementation Review, conformance or stakeholder acceptance. Return an independent current verdict over the complete selection.

A product that deviates from a recorded design criterion while every requirement still holds is not a defect; note the deviation and ask the author to record the new choice.
