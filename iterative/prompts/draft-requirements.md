# Define the agreed scope as individual obligations

Apply the supplied shared product-quality skill before authoring or reviewing.

Read the stakeholder request. Before drafting, agree an **operating profile** with the stakeholder as one batched decision, recorded with the other stakeholder decisions: (1) who supplies and who consumes each boundary (the product's own components, named operators, any outside party); (2) which faults matter and which outcomes they must not break; (3) which platform components are trusted as given (for example the runtime's standard HTTP server, the standard JSON parser and the browser), whose documented behaviour, limits and rejections the product accepts rather than re-specifies; (4) which numbers the stakeholder actually cares about (deadlines, limits, tolerances); (5) which failures saved data must survive: a process crash or kill, an operating-system crash, or power loss (recommend process crash or kill); a derived obligation's wording never raises this level; (6) the default for everything else: an action rejected before it takes effect gives a clear reason and preserves the user's data, with exact codes and wording left as design criteria; displayed status truthfully reflects rejection, staleness or uncertainty; where it is uncertain whether an operation took effect, settle the required outcome with the stakeholder; limits on input and edge cases outside ordinary use (text, date and size extremes) are the author's design decisions, recorded as stated limits, not stakeholder questions; (7) the **proportionality floor**: a timing race inside a window where the user has already been shown that something is uncertain (a failure was shown, or a leave-page or unsaved-changes warning was accepted) gets only the protected outcomes: no success shown for an unconfirmed change; no newer data overwritten by older; no old result shown as current without a stale or uncertain marker; no crash or corruption; the next valid action still works. A narrower ordering case that keeps every protected outcome is nonblocking and recorded in the finding ledger (review-policy); one that breaks any of them, or falls in severity classes 1–3, stays blocking. Agree the floor now, not once review findings start to repeat, and record its text so the endgame (skills/endgame.md) can quote it word for word. Recommend a default; the stakeholder decides. For input outside the profile, the protected outcomes are: no crash; no bad, old or unreadable value shown or acted on as current; later valid input still works. A value that passes every application check is good whatever message carried it. Do not constrain raw input size or shape beyond what the trusted parser does.

Write stakeholder REQ statements only, in the stakeholder's own terms, using the typed-requirements skill. Each states one outcome or constraint the stakeholder asked for or decided, at stakeholder granularity (one outcome the stakeholder would recognise), and its source names the intent sentence or decision it comes from. Give independent stakeholder outcomes separate roots, but split finer detail of one outcome at the software level, not into more roots. A stakeholder REQ contains no interface clause references, no protocol or representation detail and no number the stakeholder did not state. Do not add universal or negative obligations ("every", "never", "refuse all") unless the stakeholder stated them. Classify every open point with the design-criteria skill before asking about it. Ask the stakeholder only about outcomes they own; decide the rest yourself as design criteria; record what you cannot decide and cannot yet ask as provisional requirements to close before the branch that needs them is elaborated. List any obligation you believe is needed but the stakeholder did not ask for as a **derived obligation** with its reason in the RQS body. Before requesting review, send the stakeholder the plain-language root list and the derived obligations, and record the stakeholder's confirmation, changes and each derived obligation approved or declined. Record no ICD yet; `elaborate-requirements` records each one with the group whose children first need that boundary. Apply the shared author checklist and record the per-system architecture/depth rationale. The next independent Review judges these roots on their own. After the roots pass, build and run a thin end-to-end walking skeleton against those reviewed outcomes, using provisional design choices, before software elaboration. This is exploratory source work, not publication of an IMP. Record the run in the run notes (a formal OBS instead follows the existing EXP/TRY/VFY/RES route). Before elaborating each affected branch, review what the skeleton showed, keep, promote or discard its design choices, and close that branch's provisional questions with the stakeholder. No provisional requirement in the selected formal scope may remain open when its first IMP is published. Then `elaborate-requirements` adds one decomposition group at a time and each group gets its own review.

Use the supplied direct proposal guidance and payload schema. The CLI supplies identities, exact required links and publication markers. Submit the authored values with mdlm proposal submit. Keep the body empty when the structured payload and concise rationale suffice. For useful descriptive supporting specification, follow typed-requirements' owning-REQ body guidance; all required duties remain in normative fields or exact ICD clauses.
