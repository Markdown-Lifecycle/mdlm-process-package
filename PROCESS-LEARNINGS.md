## System allocation and software refinement are distinct, issue1068

Defect class: authoring guidance confused system allocation with software refinement. Record one-or-many element allocation and contributions in the owning rationale, with required duties in EARS or exact ICD clauses. The component field remains software responsibility scope. Choose system-element, software-item and internal-part boundaries explicitly; process count and label equality do not replace that judgment. Permit useful nested roles while keeping immediate-group adequacy and rejecting redundant or reversed abstraction.

Check one rooted graph with nested system, HLR and LLR links, package loading and actual resolved author/reviewer skill content. Independent review must inspect single-element and joint allocations, justified internal scope changes, and a counterexample where endpoint duties all hold but parent progress fails. Structural graph acceptance alone proves none of those semantic judgments. Preserve historic graph/field values without cosmetic migration.

## Stage requirements so each review judges one group, kernel issue 1088

Class 1 route completeness, with class 6 guidance. Watt Watch V1 (`mdlm-iterative@2.5.26`) drafted all 30 REQs and 12 DCPs in one set, and every requirements review judged the whole set: rounds 1–3 failed and round 4 passed, from 11:44 to 13:20. Most findings were missing stakeholder intent (feed cardinality, a mistyped circuit, midnight tolerance, malformed-response precedence, meter response time) that only deep review found. A failed whole-set review gives no credit, so each round re-assessed everything. Verification then fanned out to 38 activities on one shared verifier repository, so each library fix revised all of them.

Draft and review stakeholder roots first. Then add one decomposition group per autonomous `elaborate-requirements` transaction and review only that group. The kernel keeps earlier passed records unchanged, and existing review credit narrows the assessment rows. Implementation waits for a complete graph. Write verification per passed leaf group, and freeze or version the shared verifier library before activities fan out. Stakeholder refinement keeps its authority because it changes intent rather than elaborating it.

Check package loading and the eligibility in `tests/staged-requirements.mjs`. Compare review rounds and timings in a fresh staged run from the same stakeholder intent. One run is a comparison, not proof of a general improvement.

## Bound interface inputs and check joint satisfiability before requirements pass, issue 36

Class 6 review guidance. Both Watt Watch runs spent most of their late time on implementation reviews that kept failing on HTTP request edge cases. The baseline run (`mdlm-iterative@2.5.26`) hit CONNECT and Expect; the staged run (`2.5.40`) hit the Host header, the header-size ceiling (16 KB, then 1 MiB) and the request body over four review rounds. The cause was in the requirements. RF-2 refused "every request that is not a conforming feed request" while defining conformance by method and target only, so each review found the next unstated input case, and raising a finite ceiling never closed the universal claim. The clauses also could not all hold together: a 500 ms answer deadline from the end of the headers against a duty to refuse a malformed body. Requirements review passed both, although `record-interface` already asked authors to bound every numeric and length field. Stakeholder clarification 1 (Q1, 2026-10-15) settled it by declaring that feed requests carry no body. Evidence: staged-run friction notes F13 and F14.

Requirements review now checks that every incorporated interface input dimension is bounded or explicitly unbounded with a rationale, marks an unbounded universal clause `needs-change` unless its domain is settled, and checks joint satisfiability with a concrete counterexample input. Interface and drafting prompts ask authors for the same. Check package loading. At the next fresh staged run, preserve the first root-stage review and see whether it asks for these bounds before implementation.

## Bound scope with an operating profile and one review policy, issue 40

Class 6 requirements and review guidance. In Plant Pulse (`mdlm-iterative@2.5.44`), roots cited interface clauses, ICDs refused every request outside a grammar the product re-specified, and implementation review failed five times on parser corners no caller sends; the implementation phase took 4 h 32. A control re-run under the same prompts reproduced the pattern with a different author. A treatment package (`2.5.90`) agreed an operating profile first, wrote stakeholder-language roots, recorded ICDs per group trusting platform parsers, limited off-profile input to containment, and added a severity filter and a two-round stop rule. It reached acceptance in 3 h 04 with one passing implementation review. The run also showed three gaps that this entry fixes. Containment worded as "last good data unchanged" re-created a universal obligation until it was restated as protected outcomes (treatment decision 16, friction F11). `revise-interface` still asked for one general refusal (F1). The severity rule lived in `product-quality`, which verification adequacy review does not load, and 16 of 27 adequacy reviews failed on hypothetical alternative products (F13). Evidence: `deep-dive/SYNTHESIS.md` §4–5, `deep-dive/experiment/treatment.diff`, `plant-pulse-exp-run/notes/friction.md` and `metrics.md`.

This replaces the "refuse everything outside it with one general rule" sentence in `record-interface`, `revise-interface` and `product-quality`, the "blocking however unusual the input" paragraph in `product-quality`, "so the case is refused" in `correct-requirements-after-review`, and the "record the ICDs they depend on" step in `draft-requirements`. Severity, single-pass and stop rules now live once in `skills/review-policy.md`, loaded by every review type; `tests/review-policy.mjs` checks the export. One run per arm is a comparison, not proof. At the next fresh run in a different domain, count implementation-review rounds and adequacy failures that cite a product outside the profile.

## Share verification check rules and dry-run oracles, issue 42

Class 6 verification guidance. After scope was bounded, verification oracles were the largest remaining cost of the Plant Pulse treatment run (`mdlm-iterative@2.5.90`): 16 of 27 adequacy reviews failed, none on a defect in the real product. Each failure class recurred until the author made a root-cause decision that became a shared rule: one interval bracket for timing (F15), the platform's own visibility semantics on constrained elements only (F14), and integration claims at stable checkpoints only, leaving continuous preservation to component activities (F17). Repeated "stricter" rounds produced a bracket that could never pass a punctual product, and only the author's dry run caught it, because adequacy review does not run the verifier (F16). Per-group fan-out let one leaf fall outside every activity until `mdlm verification status` ran after the first execution round (F18). Evidence: `plant-pulse-exp-run/notes/friction.md` F14–F18, `deep-dive/SYNTHESIS.md` §4 point 5 and recommendation 2.

The rules now live once in `skills/verification-checks.md`, loaded by `plan-verification` and `review-verification`; `tests/review-policy.mjs` checks the adequacy-review export. They add guidance rather than replace a sentence: the package had no timing, visibility, checkpoint or dry-run rule. At the next fresh run, count adequacy failures per activity and any oracle that a dry run shows cannot pass.

## Outcomes are requirements, mechanisms are design decisions, issue 44

Class 6 requirements guidance. Across four accepted runs, 88 of 155 final requirements mixed a stakeholder outcome with the author's mechanism, and internal budgets, exit codes and polling intervals received the same review, verification and implementation-review rigor as outcomes (`deep-dive/DESIGN-criteria.md`, T8). In the Markdown Editor pilot (`mdlm-iterative@2.5.91`) against a 2.5.46 control, recorded design decisions and reclassification worked in both directions and adequacy failures fell from 14 to 6. The walking skeleton surfaced undo/redo before any software requirement; the control found it only at acceptance and paid a rejection and 50 minutes of rework. The pilot was not smaller or faster: a derived obligation worded "crash or power loss", provisional questions about races inside already-warned windows, and rollback, queues, order stamps and polling chosen to hold them produced most of its 19 implementation-review findings, while the control held the same outcomes with an atomic write, a flush and one request at a time. Stakeholder roots also grew too fine (Chore Rota: 27 roots). Evidence: `deep-dive/SYNTHESIS.md` §6–7, `deep-dive/DESIGN-criteria.md`, `deep-dive/demos/observations.md` (Markdown Editor), `deep-dive/pilot/pilot.diff`.

The new `skills/design-criteria.md` holds the classification, recording, rigor and reclassification rules, plus four defaults the pilot lacked: simplest mechanism for a protected outcome, protected outcomes only inside a warned window, durability from the operating profile only, and edge-case limits as author decisions. `draft-requirements` adds the durability and default profile items and the walking skeleton; it and `review-requirements` keep roots coarse. One paired run is a comparison, not proof, and the stakeholder designed the package. At the next fresh run, count implementation-review findings that trace to mechanisms the requirements did not need, and whether the skeleton surfaces a missing stakeholder need before software elaboration.

## Dry runs earn no credit; one frozen pass does, issue 46

Class 6 endgame guidance. In the three large runs (Ledger, Tracker, Clinic), re-running every activity after each product change took 30–46% of elapsed time; a one-line fix cost 5.5–7 h (Tracker), ~8 h (Clinic) and 1–3.5 h (Ledger). Pre-review and dry runs found most late defects, but only when they replayed at runtime: Tracker's held-request replays found regressions source checks missed and Clinic's class sweep found nine defects before an 8 h pass, while Tracker's first static sweep introduced two. A dry-run summary that read an error as a pass cost Tracker a ~2 h restart (D92). Clinic's line-start extraction of findings missed 5 of 49. A stakeholder rule to stop when only small findings remained did not cover a later credential and wrong-value defect, and both Tracker and Clinic ended without formal acceptance but with no state that said so. Evidence: `deep-dive/large-review/PROPOSAL.md` P2, P5, P8; `Q1-time.md`; `Q3-convergence.md`; `Q5-fixes.md` rank 3.

The new `skills/endgame.md` orders the end of formal work: dry runs of affected activities, class-wide pre-review with runtime replays, a full dry run with a mechanically parsed result, one for-credit pass on a single frozen version, implementation review and acceptance. Until kernel issue 1111 adds `mdlm execution dry-run`, a dry run invokes the committed verifier directly. `skills/review-policy.md` adds the finding ledger, a stakeholder checkpoint after every review with five severity classes, and the terminal state "stopped with findings, informal verdict". This adds guidance; it does not reuse results across product changes, which still needs kernel support (PROPOSAL K2, P1). At the next large run, measure elapsed time in formal execution against dry runs, count for-credit passes per accepted product, and check that every review finding has a ledger row.

## Screen truth, identity scenarios, evidence size and proportionality, issue 47

Class 6 verification guidance from the three large runs (Ledger, Tracker, Clinic). Adequacy review failed 357 of 918 reviews (39%). Tracker took about 20 display and timing rounds, nine for the worst activity, before freezing judged criteria, capturing cheaply and citing a frame and time per sample; floor-versus-verdict disputes repeated until the stakeholder ruled floors necessary-only. Tracker's credential and wrong-record defects (passwords delivered across accounts, wrong-user writes, epoch and version reuse after restore) came from the restore × session × account family across three review rounds and closed only when the server refused stale-epoch and mismatched-account mutations before any write, 29 endpoints × 2 refusals. Tracker's review packet reached 952 MiB and cost 5–6 h of restructuring; Clinic's could not be registered at all. Ledger's restore inspection kept finding ever more crafted edge cases (3, 1, 1, 1 findings over four candidates), yet the same inspection caught its over-correction rejecting valid backups. Evidence: `deep-dive/large-review/PROPOSAL.md` P3, P4, P6, P7; `Q3-convergence.md`; `Q4-verification.md`; `Q5-fixes.md` ranks 6, 8 and 13.

`skills/verification-checks.md` adds four rules: screen truth, session and identity risk scenarios, evidence size and proportionality. They add guidance rather than replace a sentence. The identity rule checks refusal at the server as a black-box outcome and reports a requirements gap instead of asserting beyond the requirements; evidence size is a planning projection until the kernel streams the packet (PROPOSAL K1). At the next large run, count display and timing adequacy rounds per activity, identity-family findings after the first implementation review, the projected against the actual packet size, and inspection findings marked out of bounds.

## Endgame lessons from large run 2, issue 53

Large run 2 (Clinic, package 2.5.48) followed the new endgame and exposed six gaps. For-credit pass #1 ran on an IMP published before class-wide pre-review, which then found four blocking defect families; with no route to a corrected IMP before credit, the pass and the implementation review that had to fail on it were wasted. Implementation reviews #2 and #3 found stale-display variants a few at a time (3, then 9 blocking), and the stakeholder-required class-wide sweep over 90 areas found 32 root defects in five rounds (16, 6, 4, 4, 2), after which review #4 found no blocking stale-display finding. The tail stopped only when the stakeholder capped the sweep and made the A6 proportionality floor explicit (decision 03); it had been set as a design default at the operating profile but not agreed as a stakeholder rule. One implementation reviewer could not judge 32 browser cases across hundreds of frames and marked them all incomplete; per-activity inspectors did. A reply written in the run's own thread cost 21 idle minutes before the stakeholder saw it, and hourly progress snapshots lapsed for about 3.5 h during the endgame. Evidence: `deep-dive/large2/stakeholder-log.md` (standing decisions 01–03), `deep-dive/large2/LAUNCH.md`; `clinic2-run/notes/friction.md`, `metrics.md`, `progress.md`.

`skills/endgame.md` gates the for-credit pass on a clean pre-review, adds the class sweep with a stakeholder-agreed round cap, the floor in every sweep, inspector and reviewer brief, per-activity inspectors and progress snapshots. `draft-requirements` asks for the floor as operating-profile item 7, and `skills/review-policy.md` sends checkpoints through the stakeholder's own channel. At the next large run, count for-credit passes started with open pre-review findings (target 0), blocking findings per implementation review after a sweep, sweep rounds against the cap, browser cases marked incomplete by implementation review, and gaps between progress snapshots.
